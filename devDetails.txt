Q1: What core business and technical problem does this Multimodal Agentic RAG system solve, and how does it fundamentally differ from standard naive text-based RAG pipelines?
----------------------------------------------------------------------------------------------------
Context:
The interviewer is assessing your domain knowledge, understanding of real-world document complexity, and ability to distinguish an enterprise-grade agentic multimodal RAG system from a naive vector search tutorial.

Developer Answer:
"Enterprise knowledge is rarely stored in clean, homogeneous, plain-text markdown files. In organizations, core intellectual property—such as system architecture specifications, competitive engineering benchmarks, algorithmic trade-offs, and compliance blueprints—resides in rich Microsoft Word (.docx) documents.

These enterprise documents possess three heterogeneous modalities that break standard naive RAG pipelines:
1. Complex Hierarchical Text: Sections, subsections, and deeply nested bullet points where the meaning of a paragraph depends entirely on its parent headings (e.g., a paragraph stating 'Cost is $0.002 per 1k tokens' is completely meaningless if divorced from its parent heading 'OpenAI GPT-4o Mini Pricing').
2. Multi-Column Structured Comparison Tables: Dense side-by-side matrices (e.g., 'RAG vs Fine-Tuning' across axes of latency, training compute, data freshness, and hallucination rate). Naive character splitters cut across table rows arbitrarily, destroying column alignment, headers, and semantic relationships.
3. Embedded Visual Architectures & System Diagrams: Flowcharts, neural network architectures, and sequence diagrams embedded as binary image objects. Naive text splitters discard binary images entirely, losing critical workflow knowledge.

Traditional Naive RAG pipelines suffer from four critical deficiencies:
- Semantic Loss & Orphan Chunks: Text chunks lose their parent document breadcrumb context.
- Modality Blindness: Complete inability to process or surface embedded diagrams and Markdown tables.
- Rigid Single-Shot Retrieval: Naive RAG executes one vector search and passes the top-K chunks to the LLM. If the retrieval is off-target, incomplete, or requires comparing two disparate sections, the LLM hallucinates or returns an incomplete response.
- Prohibitive Latency & Token Burn: Every query—even identical or semantically identical questions ('What is vibe coding?' vs 'Can you explain vibe coding?')—incurs full vector search overhead and expensive external LLM API inference.

Our Multimodal Agentic RAG system solves this holistically:
- Multimodal Ingestion: Ingests .docx files, tracks hierarchical breadcrumbs (`[Context: Heading 1 > Heading 2]`), transforms tables into pristine GitHub-Flavored Markdown, and extracts embedded binary diagrams into local assets while synthesizing semantic captions via vision models.
- Consolidated Storage: Stores 414 dense vector embeddings (384-dimensional) alongside rich metadata in a single, ACID-compliant PostgreSQL database using the `pgvector` extension with an HNSW index.
- Agentic Tool Reasoning: Replaces static chains with an autonomous LangChain tool-calling agent (ChatGroq Qwen 2.5 27B / LiteLLM Gateway) that can iteratively search, refine queries, inspect tables, and synthesize grounded answers with explicit citations.
- 2-Tier Caching: Deploys an ultra-fast L1 In-Memory TTLCache (<1ms) paired with an L2 PostgreSQL pgvector Semantic Cache (cosine similarity >= 0.78, ~30ms), slashing LLM token spend by up to 80% and delivering instantaneous responses for recurring queries."


Q2: What specific modalities and document artifacts does the system ingest, and what are the primary engineering challenges associated with each modality?
----------------------------------------------------------------------------------------------------
Context:
The interviewer wants to know how deeply you understand document parsing internals and the technical hurdles of handling diverse data types within a unified embedding space.

Developer Answer:
"Our system specifically ingests and harmonizes three distinct modalities from Microsoft Word documents:

1. Hierarchical Narrative Text:
   - Challenge: A standard paragraph in a technical document inherits context from multiple heading levels above it. If a chunker splits text naively based on 500-character windows, a chunk might say: 'It requires an upfront investment of 40 hours of compute.' The LLM cannot know whether 'It' refers to Full Fine-Tuning, LoRA, or Pretraining.
   - Solution: Our `DocumentLoader` maintains a dynamic heading stack during XML paragraph traversal. Every extracted paragraph is automatically prepended with a synthesized breadcrumb header: `[Context: Section > Subsection > Topic]`.

2. Structured Comparison Tables:
   - Challenge: Word tables are stored as nested XML structures (`<w:tbl>`, `<w:tr>`, `<w:tc>`). Slicing a table across arbitrary character boundaries leaves partial rows without header rows, rendering the data illegible to embedding models and LLMs.
   - Solution: We extract tables as atomic units, parse the header row, normalize cell text (handling line breaks and whitespace), and convert each table into a standard GitHub-Flavored Markdown table. Furthermore, we inject a synthetic descriptive header containing the table's context and surrounding section title.

3. Embedded Visual Architectures & System Diagrams:
   - Challenge: Diagrams (PNG, JPEG, EMF) are stored as raw binary image streams inside the docx ZIP container (`word/media/imageX.png`). Text embeddings cannot index raw pixel bytes directly.
   - Solution: Our pipeline extracts image parts via document relationships (`rel.target_ref`), decodes them using `Pillow`, and writes them to `data/extracted_images/image_XX.png`. Then, our `image_captioner.py` uses a Vision LLM (Groq Llama 3.2 Vision) to generate dense technical descriptions of the diagram's architecture, components, and data flow. These descriptions are embedded into the vector store with metadata pointing back to the static image file path."


Q3: How does the system guarantee groundedness and eliminate hallucinations when answering complex technical queries?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your knowledge of RAG reliability, prompt engineering guardrails, citation mechanisms, and hallucination mitigation.

Developer Answer:
"To guarantee deterministic groundedness and eliminate hallucinations, we implement strict guardrails across three architectural layers:

1. Prompt-Level Guardrails (System Prompt Constraints):
   - Mandatory Tool Usage: The system prompt explicitly commands the reasoning LLM: 'Always call search_document at least once before answering any factual or comparison question.'
   - Refusal Enforcement: The agent is instructed: 'If the answer truly isn't in the document, say so clearly instead of making something up.'
   - Citation Requirement: 'Cite the source file name(s) and relevant section(s) at the end of your answer.'

2. Context-Enriched Retrieval Formatting:
   - When the `search_document` tool executes a vector query against PostgreSQL, it does not return bare text. It enriches each retrieved passage with structured metadata:
     `[Context: Section Header > Subsection Header] [Type: table|text|image] [Source: AI-Notes.docx]`
   - This metadata explicitly anchors the LLM's attention mechanism to the authoritative section of the document.

3. Multimodal Diagram Verification:
   - For queries concerning system architectures or visual workflows, the tool returns the image's synthetic caption alongside its exact file path (e.g., `image_path: data/extracted_images/image_25.png`).
   - The agent is forced to reference the components visible in the diagram and provide the image link, which our FastAPI backend and embedded UI transform into an interactive, clickable lightbox modal."


Q4: How does the application balance end-user response latency with deep reasoning depth?
----------------------------------------------------------------------------------------------------
Context:
The interviewer is probing your ability to design low-latency systems without compromising on agentic reasoning quality.

Developer Answer:
"Agentic workflows inherently introduce latency because the LLM performs multiple iterations: query interpretation, tool call generation, tool execution, context ingestion, and final answer synthesis. In standard setups, this can easily take 6 to 12 seconds.

We balance latency and reasoning depth through a four-pillar optimization strategy:

1. 2-Tier Multi-Level Caching:
   - Tier 1 (In-Memory TTLCache): Sub-millisecond (<1ms) response for exact repeated questions.
   - Tier 2 (PostgreSQL pgvector Semantic Cache): Sub-50ms response for semantically equivalent or paraphrased questions (cosine similarity >= 0.78).
   - This completely bypasses the agent and LLM for a significant percentage of production traffic.

2. Groq LPU (Language Processing Unit) Acceleration:
   - We utilize ChatGroq running open-weights reasoning models (Qwen 2.5 27B / GPT-OSS 20B) on Groq LPUs.
   - Groq delivers inference speeds exceeding 450–600 tokens/second, reducing raw generation time from ~4,000ms (on standard GPU cloud providers) to ~400–600ms.

3. Sub-300ms FastAPI Server Initialization:
   - All heavy models, vector stores, and database pools use lazy singleton loading. The server boots in ~280ms, making it instantly responsive to container orchestrator health checks.

4. Bounded Agent Tool Iterations:
   - We configure `max_iterations=5` on `AgentExecutor` and set a 30-second request timeout on the LiteLLM gateway, preventing infinite reasoning loops or runaway token consumption."

Q6: Why was an Agentic Tool-Calling architecture chosen over a static LangChain `RetrievalQA` or LCEL chain?
----------------------------------------------------------------------------------------------------
Context:
The interviewer evaluates your understanding of modern agentic design patterns vs legacy static chains.

Developer Answer:
"Static retrieval chains (such as `RetrievalQA` or a basic LCEL pipeline: `prompt | llm | StrOutputParser`) follow a linear, inflexible DAG:
`User Query -> Embed -> Retrieve Top-K -> Stuff into Prompt -> LLM Generation`.

This static pattern fails in technical enterprise search for three reasons:
1. Multi-Hop Query Failure: If a user asks 'Compare the memory footprint of HyDE versus Dense Retrieval', a static chain performs a single search. If that search retrieves only HyDE details, the LLM must guess or hallucinate the Dense Retrieval details.
2. Inability to Reformulate Queries: If the user's question uses terminology different from the document's headers, the first retrieval might return low-relevance chunks. A static chain has no mechanism to evaluate retrieval quality and try a different query.
3. Lack of Autonomous Tool Orchestration: In an enterprise setting, an assistant may need multiple tools (e.g., `search_document`, `lookup_table`, `calculator`, `fetch_latest_nav`). Static chains cannot dynamically choose which tool to call.

Why Agentic Tool-Calling (`create_tool_calling_agent`):
- Dynamic Iteration: The agent inspects the user query, calls `search_document`, evaluates the returned passages in its scratchpad (`MessagesPlaceholder`), and if necessary, executes a second targeted search to gather missing context before generating the final answer.
- Self-Correction: If the initial query returns unrelated sections, the model autonomously rephrases the search terms.
- Deterministic Guardrails: The agent can choose NOT to call the retriever if the user asks a conversational question, or call it multiple times for complex multi-part comparisons, bounded by `max_iterations=5`."


Q7: Why did you select `ChatGroq` (specifically Qwen 2.5 27B / GPT-OSS 20B) as the reasoning core rather than standard OpenAI GPT-4o?
----------------------------------------------------------------------------------------------------
Context:
The interviewer wants to understand model evaluation criteria, hardware accelerator advantages, and cost/performance trade-offs.

Developer Answer:
"Selecting an LLM provider for an agentic application involves balancing three variables: Tool-Calling Accuracy, Token Generation Latency, and Operational Cost.

1. Inference Latency & Groq LPU Architecture:
   - In an agentic tool-calling loop, latency is multiplicative: Latency = (Time to generate Tool Call JSON) + (Retriever Execution) + (Time to generate Final Synthesis).
   - Standard GPU cloud providers (NVIDIA H100/A100 instances hosting closed or open models) typically run at 50–90 tokens/second. Two agent round-trips can easily take 6–8 seconds.
   - Groq’s Tensor Streaming Processor (LPU) architecture achieves deterministic execution speeds of 450–600 tokens/second. The agent’s tool call JSON is generated in ~120ms, and the final response synthesizes in ~600ms, making the agent feel instantaneous.

2. Open-Weights Excellence (Qwen 2.5 27B):
   - Qwen 2.5 27B is one of the strongest open-weights models for structured JSON output, markdown table comprehension, and function calling, rivaling proprietary 70B+ models while maintaining a lightweight context footprint.

3. Cost Governance:
   - Calling GPT-4o on every turn and every tool-iteration in an enterprise environment becomes cost-prohibitive ($2.50 to $10.00 per 1M tokens).
   - ChatGroq provides an order-of-magnitude lower cost structure, which, when combined with our 2-Tier Caching layer and LiteLLM gateway, slashes enterprise operating expenses by over 85%."

Q9: How does the custom `DocumentLoader` extract hierarchical text paragraphs while preserving parent document structure?
----------------------------------------------------------------------------------------------------
Context:
The interviewer wants to understand how you parse Word document XML and solve the 'lost-in-the-middle' context problem.

Developer Answer:
"Standard Word document parsers (like naive python-docx text dumpers or basic unstructured loaders) iterate over paragraphs and output flat strings. When a document has five levels of headings, chunks extracted from deep subsections lose all relationship to the primary topic.

In `src/document_loader.py`, we implement a stateful Heading Stack Tracker:
1. XML Style Inspection:
   - As we iterate through `doc.paragraphs`, we inspect the `p.style.name`.
   - Microsoft Word assigns styles like 'Heading 1', 'Heading 2', 'Heading 3', etc.
2. Dynamic Stack Maintenance:
   - We maintain a breadcrumb list: `current_headings = []`.
   - When a 'Heading 1' is encountered, the stack is reset: `['Artificial Intelligence']`.
   - When a 'Heading 2' appears, it appends: `['Artificial Intelligence', 'Retrieval-Augmented Generation']`.
   - When a subsequent 'Heading 2' appears, it pops the previous Heading 2 and replaces it, preserving the exact hierarchical tree.
3. Breadcrumb Enrichment:
   - For every body paragraph extracted, we synthesize a breadcrumb prefix:
     `[Context: Artificial Intelligence > Retrieval-Augmented Generation > Naive vs Advanced RAG]`
   - This breadcrumb is prepended to the chunk text before embedding. When vector search calculates cosine similarity, the embedding captures both the granular sentence semantics and the high-level categorical context."


Q10: How does the system extract, format, and preserve multi-column comparison tables without losing spatial semantic relationships?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your approach to tabular data in RAG, which is notoriously difficult for LLMs to interpret if flattened into plain strings.

Developer Answer:
"In technical documentation, tables contain dense, structured comparisons (e.g., comparing Dense vs Sparse Retrieval across Dimensions, Compute Requirements, and Out-of-Domain Generalization).

In `src/document_loader.py`, we handle tables with a dedicated extraction pipeline:
1. Table Element Traversal:
   - We iterate over `doc.tables`.
   - Each table's rows (`table.rows`) and cells (`row.cells`) are traversed.
2. Header Row Extraction:
   - The first row is extracted as the canonical column schema (e.g., `['Feature', 'Dense Retrieval', 'Sparse Retrieval (BM25)']`).
3. Cell Normalization:
   - Cells often contain internal line breaks (`\n`), trailing tabs, or bullet characters. We strip extraneous whitespace while preserving intra-cell formatting.
4. GitHub-Flavored Markdown Conversion:
   - We format the table into standard markdown syntax:
     ```markdown
     | Feature | Dense Retrieval | Sparse Retrieval (BM25) |
     | :--- | :--- | :--- |
     | Embedding Space | 384-1536 dim dense vectors | High-dim sparse lexical vectors |
     | Semantic Match | Matches intent & synonyms | Matches exact keywords & tokens |
     ```
5. Contextual Encapsulation:
   - We prepend the table with the nearest preceding heading breadcrumb so the table is never orphaned.
6. Atomic Preservation:
   - In `src/chunker.py`, tables are treated as indivisible semantic units. They are never sliced across rows by the character splitter, ensuring the LLM always receives the entire table schema and data rows intact."


Q11: How does the system extract embedded architecture diagrams and system flowcharts from the `.docx` archive?
----------------------------------------------------------------------------------------------------
Context:
The interviewer is assessing your knowledge of OpenXML / docx internal packaging and binary media extraction.

Developer Answer:
"A `.docx` file is an Open Packaging Convention (OPC) compliant ZIP archive containing XML files and media assets. Embedded images are stored under the `word/media/` directory within the archive.

Our extraction process in `src/document_loader.py`:
1. Relationship Traversal:
   - We access `doc.part.rels`.
   - We inspect relationship targets for image content types (`http://schemas.openxmlformats.org/officeDocument/2006/relationships/image`).
2. Binary Stream Extraction:
   - For each image relationship, we access the underlying binary blob: `rel.target_part.blob`.
3. Image Verification & Format Normalization:
   - We wrap the byte stream in `io.BytesIO` and open it via `PIL.Image.open()`.
   - This validates that the binary is a valid image format (PNG, JPEG, TIFF, BMP).
4. Deterministic On-Disk Persistence:
   - Images are saved to `data/extracted_images/image_{idx:02d}.png`.
   - In our benchmark document `AI-Notes.docx`, exactly 36 distinct architectural diagrams, neural schematics, and flowcharts were extracted.
5. Metadata Linkage:
   - Each image part records its source filename, relative path, and surrounding document paragraph position, allowing downstream components to bind the image to its parent section."


Q12: How does the multimodal image captioning pipeline work, and how does it prevent redundant, costly vision API calls?

Context:
The interviewer wants to understand vision LLM integration, prompt design for diagrams, and caching strategies for asset processing.

Developer Answer:
"Raw image binaries cannot be indexed by dense text embedding models (`sentence-transformers/all-MiniLM-L6-v2`). To make visual architectures searchable, we must translate visual diagrams into rich semantic text descriptions.

Our implementation in `src/image_captioner.py`:
1. Vision Model Selection:
   - We utilize Groq's Vision API hosting `llama-3.2-11b-vision-preview` / `llama-3.2-90b-vision-preview`.
2. Specialized Engineering Prompt:
   - Standard vision prompts ('Describe this image') generate superficial descriptions ('A diagram with boxes and arrows').
   - We use an architecture-focused prompt:
     `'Analyze this technical architecture diagram. Identify all system components, data flow directions, protocols, model names, vector databases, and steps. Provide a concise, highly detailed summary suitable for technical search retrieval.'`
3. Persistent JSON Caption Cache:
   - Vision API calls incur network latency and token cost.
   - We implement a persistent cache at `data/extracted_images/image_captions.json`.
   - On startup or re-indexing, the captioner checks if a valid caption already exists for `image_XX.png`.
   - If present, it loads the caption from disk in 0.05ms with zero API cost.
   - Only new or modified diagrams trigger an external Groq Vision API call.
4. Synthetic Document Creation:
   - The resulting caption is wrapped in a LangChain `Document`:
     - `page_content`: `[Diagram Architecture: Context: Section Name] Caption text describing workflow...`
     - `metadata`: `{"type": "image", "image_path": "data/extracted_images/image_XX.png", "section": "..."}`."


Q13: Describe the chunking strategy in `chunker.py`: How are different modalities chunked differently to maintain semantic coherence?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your expertise in advanced chunking techniques beyond basic sliding windows.

Developer Answer:
"A major flaw in naive RAG systems is applying a single homogeneous chunking rule to every document artifact. In `src/chunker.py`, we implement a Modality-Aware Chunking Strategy:

1. Text Paragraphs:
   - We utilize `RecursiveCharacterTextSplitter` configured with:
     - `chunk_size = 1000` characters
     - `chunk_overlap = 150` characters
     - `separators = ["\n\n", "\n", ". ", " ", ""]`
   - Crucially, the splitting occurs AFTER breadcrumb prefix injection. If a paragraph exceeds 1000 characters and is split into two chunks, both chunks retain the `[Context: H1 > H2]` prefix, ensuring neither chunk becomes an orphan.

2. Markdown Comparison Tables:
   - Tables are NEVER split using character windows.
   - A comparison table is treated as an atomic semantic entity. If a table contains 8 rows, splitting it at row 4 destroys the comparative analysis.
   - Each table is encapsulated into its own dedicated chunk with metadata `{"type": "table"}`.

3. Diagram & Image Captions:
   - Each diagram chunk contains the synthesized technical description, the parent section context, and the image file path.
   - Chunk size matches the caption length (~300–600 characters), accompanied by metadata `{"type": "image", "image_path": "..."}`.

Total Dataset Metrics:
From `AI-Notes.docx`, this multimodal chunking pipeline generates exactly 414 high-density, context-rich chunks (354 text chunks, 24 table chunks, and 36 image diagram chunks)."

Q14: Why choose PostgreSQL with `pgvector` (via Neon Serverless) as the vector database over dedicated vector stores like Pinecone, Milvus, or Qdrant?
----------------------------------------------------------------------------------------------------
Context:
The interviewer is evaluating your database selection rationale, total cost of ownership (TCO) considerations, and enterprise architectural maturity.

Developer Answer:
"While dedicated vector databases (Pinecone, Qdrant, Milvus) offer specialized vector search capabilities, choosing them introduces significant architectural overhead:
- Dual-Database Sync Complexity: Managing vectors in Pinecone while managing user profiles, session state, audit logs, and cache entries in PostgreSQL requires distributed two-phase commits or error-prone ETL sync pipelines.
- Cold Starts & Vendor Lock-In: Proprietary cloud vector stores carry vendor lock-in and high monthly minimum costs.
- Lack of Relational Joins: Dedicated vector stores cannot join vector search results directly with relational business tables in a single atomic SQL transaction.

Why PostgreSQL with `pgvector` (via Neon Serverless):
1. Single Unified Database: PostgreSQL serves as our vector database, relational store, metadata repository, and semantic cache database simultaneously.
2. Serverless Auto-Scaling (Neon): Neon provides scale-to-zero compute when idle, instant branching for staging/testing environments, and automated storage expansion.
3. Full ACID Guarantees: Updates to document collections and semantic cache entries are fully transactional.
4. Native SQL Ecosystem: We leverage standard SQLAlchemy, psycopg2, and `langchain-postgres` without introducing foreign query languages.

Q17: How does vector normalization affect cosine distance calculations in `pgvector`?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your mathematical understanding of vector spaces and SIMD hardware acceleration in vector retrieval.

Developer Answer:
"Cosine similarity between two vectors $\mathbf{u}$ and $\mathbf{v}$ is defined as:
$$\text{Cosine Similarity}(\mathbf{u}, \mathbf{v}) = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\|_2 \|\mathbf{v}\|_2}$$

Cosine distance is defined as:
$$D_C(\mathbf{u}, \mathbf{v}) = 1 - \text{Cosine Similarity}(\mathbf{u}, \mathbf{v})$$

In raw unnormalized vector spaces, computing cosine distance requires:
1. Computing the dot product $\sum_{i=1}^d u_i v_i$.
2. Computing the Euclidean norm of $\mathbf{u}$: $\sqrt{\sum u_i^2}$.
3. Computing the Euclidean norm of $\mathbf{v}$: $\sqrt{\sum v_i^2}$.
4. Performing floating-point division and subtraction.

Mathematical Optimization via L2 Unit Normalization:
When embeddings are normalized to unit length prior to storage:
$$\|\mathbf{u}\|_2 = 1 \quad \text{and} \quad \|\mathbf{v}\|_2 = 1$$
The formula collapses to:
$$\text{Cosine Similarity}(\mathbf{u}, \mathbf{v}) = \mathbf{u} \cdot \mathbf{v}$$
$$D_C(\mathbf{u}, \mathbf{v}) = 1 - (\mathbf{u} \cdot \mathbf{v})$$

Impact on `pgvector` Performance:
- Calculating a pure dot product uses vectorized CPU instructions (AVX-512 / AVX2 / ARM NEON) that execute in parallel across CPU registers.
- Eliminating square roots and floating-point divisions reduces vector comparison CPU cycles by over 60%, delivering faster query filtering and lower query latency under high QPS."

Q19: How does the semantic cache perform similarity matching in PostgreSQL, and how does the SQL query work?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your SQL and pgvector query construction skills, specifically looking for cosine similarity math and ANSI SQL casting.

Developer Answer:
"The L2 semantic cache persists queries in the table `rag_semantic_cache`:

```sql
CREATE TABLE IF NOT EXISTS rag_semantic_cache (
    id SERIAL PRIMARY KEY,
    normalized_query TEXT NOT NULL,
    query_embedding vector(384) NOT NULL,
    answer TEXT NOT NULL,
    images JSONB DEFAULT '[]'::jsonb,
    hit_count INT DEFAULT 1,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_rag_semantic_cache_norm_query 
ON rag_semantic_cache (normalized_query);
CREATE INDEX IF NOT EXISTS idx_rag_semantic_cache_vector 
ON rag_semantic_cache USING hnsw (query_embedding vector_cosine_ops);
```

When a new query misses L1, `src/cache.py` generates the 384-dimensional embedding using `all-MiniLM-L6-v2`. It then executes the following parameterized SQL query:

```sql
SELECT response_text, sources, images,
       1 - (query_embedding <=> CAST(:embedding AS vector)) AS similarity
FROM rag_semantic_cache
WHERE 1 - (query_embedding <=> CAST(:embedding AS vector)) >= :threshold
ORDER BY similarity DESC
LIMIT 1;
```

Key Architectural Details:
1. Cosine Distance Operator `<=>`: In `pgvector`, `<=>` computes the cosine distance between two vectors. Therefore, $1 - (\mathbf{u} \Leftrightarrow \mathbf{v})$ computes the cosine similarity.
2. ANSI Standard Casting: We use `CAST(:embedding AS vector)` rather than PostgreSQL shorthand `:embedding::vector`. In SQLAlchemy, double colons (`::`) conflict with bind parameter syntax, causing parsing exceptions.
3. Threshold Tuning & Real-World Calibration (The 0.92 vs 0.78 Dilemma):
   - Configured Parameter: `CACHE_SEMANTIC_THRESHOLD = 0.78` (in `.env` and `src/config.py`).
   - The Root Cause of Duplicate Cache Insertion (Real-World Case Study):
     Consider when a user submits two semantically related prompts in sequence:
       Prompt 1: 'what are the types of machine learning?'
       Prompt 2: 'how many types of machine learning are present there noadays?'
     Under an overly strict threshold of `0.92`:
       a. Prompt 1 executes through the agent and is stored in `rag_semantic_cache`.
       b. When Prompt 2 arrives, `src/cache.py` generates its 384-dimensional dense vector (`all-MiniLM-L6-v2`) and computes cosine similarity against Prompt 1.
       c. Mathematical Result:
          Cosine Similarity = 0.7983 (~79.8%).
       d. Because 0.7983 < 0.92, the L2 semantic cache evaluates Prompt 2 as a CACHE MISS!
       e. Consequently, the application treats Prompt 2 as an un-cached query, invokes LLM reasoning, and saves Prompt 2 as a second redundant entry in `rag_semantic_cache`.
   - Why do semantically similar queries score ~0.80 instead of >= 0.92?
     1. Semantic Intent Shift: 'What are the types' is a qualitative request for category identities (Supervised, Unsupervised, RL); 'How many types are present' is a quantitative request for an entity count.
     2. Lexical & Syntactic Divergence: Additional filler tokens ('how many', 'present there') pull the sentence representation into a slightly different vector space direction.
     3. Typographical Noise: The typo 'noadays' (instead of 'nowadays') reduces similarity from 0.8378 down to 0.7983.
     4. Vector Geometry Reality: In `all-MiniLM-L6-v2`, `0.92+` is an ultra-strict threshold matching only near-verbatim duplicate phrasing (e.g. 'What is vibe coding?' vs 'Explain vibe coding'). Natural conversational paraphrases with differing grammatical structures consistently cluster between 0.75 and 0.85.
   - The Solution & Empirical Separation:
     Tuning `CACHE_SEMANTIC_THRESHOLD = 0.78`:
     - Allows Prompt 2 (0.7983 >= 0.78) to trigger an L2 Semantic Cache Hit, immediately returning Prompt 1's saved answer in ~35ms, promoting Prompt 2 to L1, and skipping database re-insertion.
     - Safely discriminates genuinely distinct questions, which score far lower:
       * Sim('Types of ML', 'Supervised vs Unsupervised differences') = 0.4024
       * Sim('Types of ML', 'Explain gradient descent') = 0.3548
     This strikes the optimal engineering balance: high conversational hit rates without false-positive collisions."


Q20: What is the 'Self-Healing L1 Promotion' pattern, and why is it critical for throughput?
----------------------------------------------------------------------------------------------------
Context:
The interviewer assesses your knowledge of cache hierarchy dynamics, data locality, and multi-tier promotion patterns.

Developer Answer:
"In multi-tiered caching systems, retrieving data from a lower, slower tier (L2 database) without promoting it to the higher, faster tier (L1 memory) is an anti-pattern known as 'Cache Starvation'.

The Problem:
If User A asks 'Explain vibe coding', it misses L1, misses L2, runs the agent, and populates both L1 and L2.
After 2 hours, L1 TTL expires.
User B asks 'Can you explain vibe coding?'.
This misses L1, but hits L2 in PostgreSQL (cosine similarity = 0.94).
If we simply returned the L2 answer without updating L1, subsequent identical requests would continue hitting the PostgreSQL database, incurring 35ms network round-trips and consuming database connection pool slots.

The Self-Healing L1 Promotion Solution:
Whenever an L2 semantic cache hit occurs in `src/cache.py`:
1. The response payload (answer, sources, images) is retrieved from PostgreSQL.
2. The exact incoming query string from User B is immediately hashed and stored into the local L1 `TTLCache`.
3. Subsequent requests with that exact phrasing now hit L1 directly in <1ms.

Benefits:
- Eliminates recurring database reads for popular paraphrased queries.
- Prevents database connection exhaustion during traffic spikes.
- Keeps the in-memory working set fresh based on real user access patterns."

Q23: How does Time-To-Cache (TTL) validity work in the Vector Embedding Cache (L2 Semantic Cache), why do naive vector caches lack it, and how is `CACHE_L2_TTL` implemented?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your understanding of vector database lifecycle management, temporal data degradation, and production cache eviction strategies.

Developer Answer:
"In traditional key-value caches (like Redis or Memcached), every key-value pair can be assigned an absolute Time-To-Live (`EXPIRE key 86400`). When the TTL expires, the storage engine evicts the key automatically.

Why Naive Vector Embedding Caches Lack TTL:
Vector databases (including PostgreSQL `pgvector`, Pinecone, Milvus, and Qdrant) are engineered for static or slowly-mutating vector indexes using HNSW or IVF graphs. By default, they do not have background TTL eviction engines. 
In naive semantic caching tutorials, developers insert a user query vector and LLM response into a table with a timestamp, but when querying for nearest neighbors:
```sql
-- NAIVE APPROACH (NO TTL)
SELECT response_text FROM semantic_cache 
WHERE 1 - (embedding <=> :query_vector) >= 0.90 
ORDER BY similarity DESC LIMIT 1;
```
This naive approach suffers from permanent cache persistence:
1. If domain documentation updates (e.g., pricing, technical APIs, or system architecture changes), a 6-month-old cached answer will continue to be served to users forever whenever cosine similarity is >= 0.90.
2. Even if documentation is static, cached answers may contain transient assumptions or deprecated model styles.

Our Time-To-Cache (TTL) Architecture in `src/cache.py`:
We introduced configurable Time-To-Cache validity for the L2 pgvector semantic cache via `CACHE_L2_TTL`:

1. Configuration Parameter:
   - Configured in `src/config.py` and `.env`:
     `CACHE_L2_TTL: int = 86400  # Default 24 hours (86,400 seconds); 0 disables TTL check (infinite)`

2. Parameterized SQL Query with Temporal Filtering:
   When `src/cache.py` queries `rag_semantic_cache`, it applies a strict temporal predicate:
   ```sql
   SELECT response_text, sources, images,
          1 - (query_embedding <=> CAST(:embedding AS vector)) AS similarity
   FROM rag_semantic_cache
   WHERE 1 - (query_embedding <=> CAST(:embedding AS vector)) >= :threshold
     AND (:ttl = 0 OR updated_at >= NOW() - (:ttl * INTERVAL '1 second'))
   ORDER BY similarity DESC
   LIMIT 1;
   ```
   If a matching query exists with cosine similarity >= 0.78, but its `updated_at` timestamp is older than `CACHE_L2_TTL` seconds, the database skips it and treats it as a cache miss.

3. Physical Eviction & Purging:
   To prevent dead rows from accumulating in PostgreSQL, we implemented `purge_expired_l2_cache()`:
   ```python
   def purge_expired_l2_cache(self) -> int:
       if self.l2_ttl <= 0:
           return 0
       with self._engine.begin() as conn:
           res = conn.execute(
               text("DELETE FROM rag_semantic_cache WHERE updated_at < NOW() - (:ttl * INTERVAL '1 second');"),
               {"ttl": self.l2_ttl}
           )
           return res.rowcount
   ```
   This can be triggered by scheduled cron jobs, background workers, or during administrative reindexing.

4. Cache Telemetry:
   `GET /api/cache/stats` exposes `ttl_seconds` under `l2_semantic_cache`, providing full observability into active cache retention policies."

     ```python
     def should_cache_response(query: str, answer: str) -> Tuple[bool, str]:
         # 1. Temporal / Real-time Query Check
         if any(re.search(pat, query.lower()) for pat in TEMPORAL_PATTERNS):
             return False, 'Skipped caching: Temporal / real-time query'
         # 2. Negative Fallback / Out-of-Document Check
         if not settings.CACHE_NEGATIVE_RESPONSES:
             if any(pat in answer.lower() for pat in NEGATIVE_ANSWER_PATTERNS):
                 return False, 'Skipped caching: Out-of-domain response'
         return True, 'Valid for cache admission'
     ```
   - Telemetry Transparency:
     - `set_cached_response()` returns structured telemetry (`cached`, `l1`, `l2`, `reason`, `error`).

Q30: Why does pure dense semantic vector search fail on specific technical acronyms and exact keyword searches (e.g., 'sparse vs dense vector embeddings'), and how does Hybrid Search resolve this?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your understanding of retrieval failure modes, vocabulary mismatch, lexical vs semantic representation spaces, and why enterprise RAG requires hybrid search.

Developer Answer:
"In production RAG systems, relying exclusively on dense vector embeddings (such as `all-MiniLM-L6-v2` or `text-embedding-3-small`) leads to subtle and frustrating retrieval failures.

The Dense Vector Search Blindspot:
Dense embedding models map sentences into a continuous, dense 384- or 1536-dimensional manifold where Euclidean or Cosine distance represents semantic proximity. However:
1. Vocabulary Mismatch & Smoothing: Dense embeddings tend to 'smooth out' distinct technical tokens. For example, queries like 'sparse vs dense in vector embeddings', 'GPT-4o vs Claude 3.5 Sonnet', or specific function names (`create_tool_calling_agent`) get mapped close to general text about 'embeddings' or 'agents'. The retriever frequently returns passages discussing dense vectors in general while completely missing passages that explicitly mention the word 'sparse'.
2. Exact Token Matching: When a user queries a specific error code (`Errno 11001`), database identifier (`ai_notes_docs`), or specialized keyword, dense embeddings score chunks based on syntactic tone rather than the literal presence of that vital token.

The Sparse Lexical Solution (BM25):
Sparse lexical search (specifically BM25 - Best Matching 25) models documents as high-dimensional, sparse vectors based on exact term frequencies:
$$\text{BM25}(D, Q) = \sum_{i=1}^{n} \text{IDF}(q_i) \cdot \frac{f(q_i, D) \cdot (k_1 + 1)}{f(q_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}
\right)}$$
- Parameters: $k_1 = 1.5$ (term frequency saturation), $b = 0.75$ (document length normalization).
- Strength: If the word 'sparse' appears in the document, BM25 assigns it a massive non-zero weight based on Inverse Document Frequency ($\text{IDF}$).

Hybrid Search Resolution:
In `src/hybrid_retriever.py`, we implement a unified `HybridRetriever`:
1. Executes dense pgvector search (HNSW cosine distance) to capture conceptual, high-level intent.
2. Executes sparse `rank_bm25.BM25Okapi` search over tokenized document chunks to capture exact keyword matches and technical identifiers.
3. Fuses both candidate lists using Reciprocal Rank Fusion (RRF), ensuring that passages satisfying both semantic intent and exact keywords rank at the very top."


Q31: Walk through the mathematical formulation and implementation of Reciprocal Rank Fusion (RRF) in `src/hybrid_retriever.py`.
----------------------------------------------------------------------------------------------------
Context:
The interviewer evaluates your knowledge of rank aggregation algorithms and why linear score combination is an anti-pattern for hybrid retrieval.

Developer Answer:
"When combining dense and sparse retrieval results, a naive developer might attempt to linearly add or multiply the scores:
$$	ext{Score}_{	ext{naive}} = lpha \cdot 	ext{Score}_{	ext{dense}} + (1 - lpha) \cdot 	ext{Score}_{\text{BM25}}$$

Why Linear Score Combination Fails in Practice:
1. Incompatible Score Scales: Cosine similarity produces scores bounded strictly between $[-1, 1]$ (or $[0, 1]$ for normalized vectors). BM25 produces unbounded scores $[0, \infty)$ where the maximum score depends on document length, query length, and corpus size.
2. Calibration Fragility: Any single parameter $lpha$ that works for 3-word queries breaks down on 15-word queries because the BM25 score magnitude scales non-linearly with query length.

The Reciprocal Rank Fusion (RRF) Formulation:
RRF is an unsupervised, scale-invariant rank aggregation algorithm developed by Cormack, Clarke, and Büttcher. Instead of combining raw score values, RRF operates purely on the ordinal ranks of items across disparate retriever lists:

$$\text{RRF Score}(d) = \sum_{m \in M} \frac{w_m}{k + 	ext{rank}_m(d)}$$

Where:
- $M = \{	ext{dense}, 	ext{sparse}\}$: The set of retrieval models.
- $	ext{rank}_m(d) \in \{1, 2, \dots, K\}$: The 1-based rank position of document $d$ in the result list of retriever $m$.
- $k = 60$: A ranking constant empirically proven to prevent items at the very top of one list from completely dominating items that appear favorably across multiple lists.
- $w_{	ext{dense}} = 0.5, w_{	ext{sparse}} = 0.5$: Balanced weights assigned to each retrieval modality.

Implementation in `src/hybrid_retriever.py`:
```python
def retrieve(self, query: str, top_k: int = 4) -> List[Document]:
    dense_docs = self.vector_store.similarity_search(query, k=top_k * 2)
    sparse_docs = self.bm25_retriever.retrieve(query, top_k=top_k * 2)

    rrf_scores = {}
    doc_map = {}

    # Accumulate Dense Ranks
    for rank, doc in enumerate(dense_docs, start=1):
        doc_id = doc.metadata.get("chunk_id", doc.page_content[:100])
        doc_map[doc_id] = doc
        rrf_scores[doc_id] = rrf_scores.get(doc_id, 0.0) + (0.5 / (60 + rank))

    # Accumulate Sparse Ranks
    for rank, doc in enumerate(sparse_docs, start=1):
        doc_id = doc.metadata.get("chunk_id", doc.page_content[:100])
        doc_map[doc_id] = doc
        rrf_scores[doc_id] = rrf_scores.get(doc_id, 0.0) + (0.5 / (60 + rank))

    # Sort descending by fused RRF score
    sorted_ids = sorted(rrf_scores.keys(), key=lambda x: rrf_scores[x], reverse=True)
    return [doc_map[doc_id] for doc_id in sorted_ids[:top_k]]
```

Benefits:
- Zero hyperparameter calibration required.
- Documents appearing in both dense and sparse retrieval receive a massive additive boost.
- If a document is only found by BM25 (e.g. an exact acronym), it still achieves a competitive rank."


Q32: What is the Cross-Encoder Re-Ranking Stage, how does it differ fundamentally from Bi-Encoder dense retrieval, and how is graceful non-blocking fallback guaranteed?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your advanced knowledge of two-stage retrieval architectures, transformer attention mechanics (Bi-Encoder vs Cross-Encoder), and production fault tolerance.

Developer Answer:
"In modern high-precision RAG systems, retrieval is structured as a two-stage funnel:
1. Stage 1: Candidate Generation (High Recall): Fast retrieval (Hybrid Dense + BM25) surfaces top 10–20 candidates in ~15ms.
2. Stage 2: Re-Ranking (High Precision): A Cross-Encoder model re-scores candidate passages to identify the top 4 most relevant chunks.

Bi-Encoder vs Cross-Encoder Architecture:
- Bi-Encoder (`sentence-transformers/all-MiniLM-L6-v2`):
  - Encodes Query $Q$ into vector $\mathbf{u} = E(Q)$ and Document $D$ into vector $\mathbf{v} = E(D)$ completely independently.
  - Similarity is calculated as a simple dot product: $S = \mathbf{u} \cdot \mathbf{v}$.
  - Advantage: Ultra-fast ($O(1)$ lookup via HNSW index); document embeddings are pre-computed offline.
  - Disadvantage: 'Information Bottleneck'—there is zero token-level cross-attention between query words and passage words during encoding.
- Cross-Encoder (`cross-encoder/ms-marco-MiniLM-L-6-v2`):
  - Ingests Query and Document concatenated as a single sequence: `[CLS] Query [SEP] Document [SEP]`.
  - All 6 transformer layers apply full bidirectional self-attention across every query token and document token simultaneously.
  - The `[CLS]` token output passes through a classification head yielding a logit score representing true relevance.
  - Advantage: Captures complex sentence semantics, negations, prepositions, and exact contextual relationships that bi-encoders miss.
  - Disadvantage: Computationally intensive ($O(N)$ transformer inferences at runtime), making it unsuitable for scanning millions of vectors, but ideal for re-ranking the top 10–20 candidates.

Implementation in `src/hybrid_retriever.py`:
```python
class CrossEncoderReRanker:
    def __init__(self, model_name: str = "cross-encoder/ms-marco-MiniLM-L-6-v2"):
        from sentence_transformers import CrossEncoder
        self.model = CrossEncoder(model_name)

    def rerank(self, query: str, documents: List[Document], top_k: int = 4) -> List[Document]:
        pairs = [[query, doc.page_content] for doc in documents]
        scores = self.model.predict(pairs)
        ranked = sorted(zip(documents, scores), key=lambda x: x[1], reverse=True)
        return [doc for doc, score in ranked[:top_k]]
```

Graceful Non-Blocking Fallback Design:
In enterprise systems, external model dependencies must never cause system outages:
1. Lazy Loading & Error Handling: If model weights cannot be downloaded (e.g. offline sandbox, missing HF credentials, or network timeout), `CrossEncoderReRanker` catches exceptions gracefully:
   ```python
   try:
       return self.reranker.rerank(query, candidates, top_k=top_k)
   except Exception as e:
       logger.warning("Re-ranking failed or unavailable (%s), falling back to RRF order.", e)
       return candidates[:top_k]
   ```
2. Result: If the re-ranker is enabled, users get state-of-the-art precision; if it is unavailable or disabled via `RERANKING_ENABLED=false`, the system seamlessly returns the top RRF-fused documents with zero downtime."

Q34: How does tool aliasing prevent agent hallucination of non-existent tools like `search_function`?
----------------------------------------------------------------------------------------------------
Context:

Developer Answer:
"A notorious issue with smaller reasoning models (20B–30B parameters) is tool name hallucination. Although the tool is declared as `search_document`, models occasionally hallucinate tool names like `search_function`, `document_search`, or `retrieve_context` based on pre-training priors.

When an LLM invokes an undeclared tool name, standard LangChain raises an unhandled `ToolException` or crashes the execution loop.

Our Tool Aliasing Guardrail in `src/tools.py`:
1. We define the primary tool `@tool("search_document")`.

   ```python
   @tool("search_function")
   ```

3. Both tools are registered in `get_tools()`.
4. If the model emits `search_document`, it executes normally. If it hallucinates `search_function`, the alias catches the call, executes the retrieval, and returns the context without interrupting the user's turn."

Q37: How is Real-Time Streaming implemented using Server-Sent Events (SSE / `StreamingResponse`), why is SSE chosen over WebSockets, and what is the event lifecycle protocol?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your knowledge of real-time web protocols, HTTP streaming, user perceived latency (Time-to-First-Token), and frontend streaming consumption.

Developer Answer:
"In generative AI applications, waiting 3 to 6 seconds for a full agentic response creates a poor user experience. To slash Time-to-First-Token (TTFT) and provide immediate user feedback, we implemented Real-Time Streaming using Server-Sent Events (SSE).

Why Server-Sent Events (SSE) Over WebSockets:
1. Unidirectional Simplicity: LLM streaming is inherently unidirectional (the client submits a query once, and the server pushes tokens back). WebSockets provide full-duplex communication, which adds unnecessary protocol complexity.
2. Standard HTTP/1.1 & HTTP/2 Compatibility: SSE uses standard HTTP connections (`Content-Type: text/event-stream`), traversing corporate firewalls, reverse proxies, and API gateways (such as Azure APIM or Nginx) without special socket upgrading.
3. Built-In Reconnection: Browsers natively support automated retry and reconnection on SSE connections via the `EventSource` / `fetch` readable stream API.

Streaming Architecture in `src/api.py`:
We provide `POST /api/ask/stream` and `GET /api/ask/stream?question=...` returning FastAPI's `StreamingResponse(media_type="text/event-stream")`.

The SSE Event Lifecycle Protocol:
The endpoint streams newline-delimited SSE chunks (`data: <json>

`) across five distinct phases:
1. Phase 1: Cache Verification (`type: status`, `stage: cache_check`)
   - Emits: `{"type": "status", "stage": "cache_check", "message": "Checking hybrid cache..."}`
   - If an L1 or L2 cache hit occurs: Immediately streams the cached text tokens and closes the stream with `done` in <40ms.
2. Phase 2: Hybrid Retrieval (`type: status`, `stage: retrieving`)
   - Emits: `{"type": "status", "stage": "retrieving", "message": "Searching documents (Hybrid BM25 + pgvector)..."}`
   - Informs the user that document retrieval, RRF fusion, and Cross-Encoder re-ranking are executing.
3. Phase 3: Generation Start (`type: status`, `stage: generating`)
   - Emits: `{"type": "status", "stage": "generating", "message": "Generating response..."}`
4. Phase 4: Token Streaming (`type: token`)
   - Emits: `{"type": "token", "content": "..."}` as tokens are yielded by the LLM stream.
5. Phase 5: Stream Completion (`type: done`)
   - Emits: `{"type": "done", "answer": "...", "images": [...], "sources": [...], "cache_status": "Agent Reasoning (Hybrid + Cross-Encoder)"}`
   - Provides final citations, multimodal diagram links, and status badges.

Frontend Consumption in `static/index.html`:
The browser consumes the stream using standard JavaScript `fetch()` and `ReadableStreamDefaultReader`:
```javascript

});
const reader = response.body.getReader();
const decoder = new TextDecoder('utf-8');

while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    const chunk = decoder.decode(value);
    // Parse 'data: {...}' lines, append tokens, and re-render Marked.js markdown
}
```
Result: Users observe generation beginning in ~300ms, transforming perceived latency from seconds to milliseconds."

"In naive Python AI applications, developers instantiate HuggingFace embedding models, PostgreSQL database connections, and LangChain agents at the root of the file (`global scope`).

The Consequence:
Importing `api.py` triggers PyTorch model weight loading, network handshakes to Neon PostgreSQL, and Groq API handshakes. The application takes 8 to 15 seconds just to start, causing container orchestrators (Kubernetes, Azure Container Apps) to fail readiness probes and kill the container.

Our Sub-300ms Lazy Initialization Strategy:
1. Root-Level Decoupling:
   - No heavy models or database connections are created at import time.
   - Global pointers are initialized to `None`: `_cached_agent = None`, `_cached_vector_store = None`.
2. Thread-Safe Double-Checked Locking:
   - In `src/agent.py` and `src/vector_store.py`, instances are created on-demand inside factory functions guarded by threading locks.
3. Rapid Lifespan Startup:
   - When Uvicorn boots `src/api.py`, it loads only standard library and FastAPI route definitions.
   - Startup time benchmarks consistently at ~250–280ms.
4. Background Warming:
   - Readiness probes ping `GET /api/health`, which can optionally pre-warm the database connection asynchronously without blocking process boot."

Q43: Explain the four primary RAGAS metrics evaluated and what aspects of the pipeline they validate.
----------------------------------------------------------------------------------------------------
Context:
The interviewer wants a precise mathematical and conceptual understanding of RAGAS metrics.

Developer Answer:
"We evaluate our multimodal RAG pipeline across four complementary RAGAS metrics:

1. Faithfulness (Measures Groundedness / Hallucination Rate):
   - Definition: The proportion of claims in the generated answer that can be directly inferred from the retrieved context.
   - Formula: $\text{Faithfulness} = \frac{|\text{Number of Claims in Answer Supported by Context}|}{|\text{Total Claims in Generated Answer}|}$
   - Pipeline Target: $\ge 0.90$. A score of 1.0 means zero hallucinated claims.

2. Answer Relevancy (Measures Query-Response Alignment):
   - Definition: Evaluates whether the generated answer directly addresses the user's prompt without introducing irrelevant tangents.
   - Computation: The Judge LLM generates $N$ synthetic questions from the generated answer, computes their embeddings, and calculates the mean cosine similarity against the original user question embedding.
   - Pipeline Target: $\ge 0.85$.

3. Context Precision (Measures Retriever Signal-to-Noise Ratio):
   - Definition: Evaluates whether the most relevant chunks are ranked at the top of the retrieved context list.
   - Formula: Mean Average Precision at $K$ ($\text{MAP}@K$) based on chunk relevance binary labels.
   - Pipeline Target: $\ge 0.80$. Validates our HNSW index and dense embedding retrieval accuracy.

4. Context Recall (Measures Information Completeness):
   - Definition: Measures whether all key facts present in the ground truth answer were successfully retrieved in the context.
   - Formula: $\text{Context Recall} = \frac{|\text{Ground Truth Sentences Attributed to Context}|}{|\text{Total Sentences in Ground Truth}|}$
   - Pipeline Target: $\ge 0.85$. Validates chunk size and retrieval $K$ sufficiency."

Q48: What are the primary failure modes of this multimodal RAG application, and how are they mitigated?
----------------------------------------------------------------------------------------------------
Context:
The interviewer tests your real-world battle scars: how do you prevent the system from crashing under stress?

Developer Answer:
"In production, AI systems fail across multiple failure domains:

1. Failure Mode: Upstream LLM Rate Limiting (HTTP 429) or Outages:
   - Risk: Groq hits request-per-minute (RPM) or token-per-minute (TPM) limits.
   - Mitigation: Our embedded LiteLLM Gateway catches 429 errors and automatically fails over to `groq/openai/gpt-oss-20b` without failing the user request.
2. Failure Mode: Database Connection Pool Exhaustion:
   - Risk: Bursts of concurrent queries exhaust PostgreSQL connection limits.
   - Mitigation: SQLAlchemy connection pooling configured with `pool_size=10`, `max_overflow=20`, `pool_pre_ping=True`, and `pool_recycle=300`. Idle connections are automatically pruned, and broken sockets are recycled.
3. Failure Mode: Image Extraction & Processing Failures:
   - Risk: Corrupted image stream inside the `.docx` archive crashes `Pillow`.
   - Mitigation: Defensive try/except blocks in `DocumentLoader` log image extraction warnings and proceed with text processing rather than aborting the entire document ingestion.
4. Failure Mode: Model Tool Name Hallucination:
   - Risk: Model calls `search_function` instead of `search_document`.
   - Mitigation: Tool aliasing in `src/tools.py` catches common hallucinations and redirects them to the canonical search implementation."


Q49: How does the system handle high concurrency and scaling across multiple worker instances?
----------------------------------------------------------------------------------------------------
Context:
The interviewer evaluates your understanding of horizontal scaling, stateless architectures, and distributed cache coherence.

Developer Answer:
"To scale horizontally across multiple container instances (e.g., 5 ACA replicas under KEDA auto-scaling), the application must maintain statelessness:

1. Stateless Server Tier:
   - FastAPI container instances maintain no sticky user sessions. Any container can serve any incoming request.
2. Distributed Vector & Semantic Cache Tier:
   - The L2 pgvector semantic cache resides in PostgreSQL. When Container 1 processes a query and writes to `rag_semantic_cache`, Container 2 and Container 3 immediately benefit from that semantic cache entry.
3. L1 Cache Local Partitioning:
   - The L1 in-memory `TTLCache` is local to each container process. This is intentional: memory reads stay within the local CPU L3 cache/RAM (<0.1ms). If higher cluster-wide cache coherence is required, the L1 layer can be swapped for a distributed Redis cluster using Redis TTL strings with zero changes to caller code.
4. Connection Pooling:
   - To prevent multiple replicas from overwhelming PostgreSQL, we utilize Neon’s built-in PgBouncer connection pooler (`pooler.c-14.us-east-1.aws.neon.tech`), allowing thousands of concurrent client connections over a compact physical database pool."
